# PR 预览产物下载故障排查

Wiki quality 的 PR 构建上传预览输入后，立即下载同一运行、PR 编号、head 和 attempt 对应的产物。首次失败后等待 5 秒重试；再次失败后等待 10 秒作最后一次下载。前两次错误可重试，最后一次失败会使任务失败。成功下载还必须通过原始压缩包字节比较和安全解包检查，重试成功并不代替这些检查。

每次下载显式设置 `digest-mismatch: error`，该参数也是 `actions/download-artifact@v8` 的默认值：摘要不匹配会使该次下载失败。下载动作的摘要校验与后续的原始 ZIP 字节比较是两道不同检查；此配置核对不代替真实错误注入验证。

工作流摘要列出每次下载及往返校验的原始 outcome。前两次失败使用 `continue-on-error`，即使重试成功，日志仍可能保留错误标注；应检查具体失败步骤，不能仅凭任务最终成功判定首次下载成功，也不能将每种错误都归因于产物可见性延迟。

## 样本与限制

2026-11-27 通过 Actions Jobs API 检查最近 8 次已完成的 PR Wiki quality 运行（44887627665 至 44809812498，2026-11-20 至 2026-11-21，UTC）：8 次最终成功且往返校验成功；其中 5 次未触发重试，3 次触发首次重试并成功。三个重试运行 44810577760、44810162428、44809812498 的日志均显示首次按名称查找产物失败，等待 5 秒后下载成功，上传与下载的 SHA-256 一致；按日志时间戳，上传完成到重试成功约 7–8 秒。这些样本跨多个 PR，但来自有限时间窗口，不能代表长期故障率，也不能证明服务端根因。

这组样本与此前 #43 中的 12 次单分支样本并非长期独立随机抽样。当前 5 秒和 10 秒等待仅是有限样本支持的折中，不保证覆盖更长故障。仍需真实运行或受控测试覆盖权限不足、服务不可用、产物真正缺失、三次均失败和摘要不匹配；不得根据成功样本声称这些负例已经验证。

2026-11-27 在 Windows、Python 3.14.9 和 Git Bash 执行 `python -m unittest tools.test_preview_roundtrip_workflow -v`：测试直接读取工作流的往返校验 shell 脚本，完整包通过；下载文件缺失、文件被追加篡改、包内容缺失均返回失败。此测试覆盖下载完成后的比较和内容检查，不模拟 GitHub 下载动作的权限、服务错误、摘要校验或 Actions 重试调度。

## 排查步骤

1. 确认上传步骤成功，记录运行 ID、attempt、PR head、产物名称与上传摘要；不要公开带凭据的下载地址。
2. 查看每次下载的日志和摘要 outcome，区分找不到产物、权限、服务错误及摘要错误；确认对应的错误和重试时间，而非只看 Jobs API 的 `conclusion`（前两次允许失败）。
3. 若全部下载失败或比对、解包失败，保持任务失败；排查权限、产物是否过期、GitHub 服务状态和日志，再按需重新运行。不要跳过字节比较或安全解包。
4. 成功重试仍有错误标注时，结合摘要和校验步骤说明最终结果。若问题持续，保存脱敏的运行链接、错误类型及时间，评估等待策略，不把所有错误当作短暂延迟。
