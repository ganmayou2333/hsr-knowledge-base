# ADR-0003 · 上下文装载与 Token 纪律

> **Status**：Accepted（2026-11-15 聚合定稿）
> **覆盖决策**：D-003
> **相关**：`格式规范与要求.md` §十二·补（Token 暂停规则）、`ADR-0001`

## Context

本库正文规模已达 `data/zh_cn/` 6,685 个 `.md`、镜像 2.2 万余文件，单份台账（`待办清单.md`）就有 105 KB / 1,316 行。
在 256k 上下文窗口下，「先把相关文档整份读进来」的做法会挤占产出空间，导致中途遗忘约束、重复劳动，甚至整轮只够读文件。

## Decision

1. **单轮装载上限**：单轮上下文装载 ≤ **80k**（约 31%），预留 ≥ **176k** 给对话与产出（D-003）。
2. **禁整份装载大台账**：`待办清单.md` 一律按节 / 按关键词检索后局部读取，不得整份推入上下文。
3. **Token 检查点**：单次任务（跨会话续作同样累计）的消耗达 **80–120 万** token 区间时，必须停工汇报「已完成 / 产物清单 / 问题 / 剩余计划与预估」，等用户明确确认后才继续；不得以「快了」为由自行续跑（规范 §十二·补）。
4. **优先按需取证**：能用一条命令得到的结论（`grep -c`、`verify_*` 输出、`git ls-tree`）不靠通读文档推断；盘点类工作交子代理，只回传结论与命令。

## Consequences

- **正面**：单轮有足够额度完成「读规范 → 改 → 跑验收 → 汇报」闭环；大库不至于把上下文吃光。
- **负面**：必须预先知道去哪查，检索能力成为瓶颈；跨文件一致性靠脚本而非人眼记忆。
- **风险**：检查点是**硬约束**，若被忽略会连续烧 token 且产出质量下降；此条与「做完的就留着」并存——停工不等于回退。
