# ADR-0001 · 协作分工与执行通道

> **Status**：Accepted（2026-11-15 聚合定稿）
> **覆盖决策**：D-001、D-016、D-017、D-021、D-050、D-051、D-052、D-054、D-055
> **相关**：`ADR-0002`（证据与权威层级）、`ADR-0013`（批量写入安全）

## Context

本库长期由三方协作：用户拍板、Lead（管理 + 审核 + 写规范/工单/文档，不写五语数据文件）、执行方（写数据文件）。
执行方经历过两次迁移：豆包桌面版（经 CDP 消息通道）→ 会话内 DSH 子代理。期间出现两类系统性风险：

1. **通道能力被高估**：D-016 曾判定豆包「无 MCP 工具」，其会话里的「已回报 / 已完成」属角色扮演式虚构；D-021 又实测它具备真实文件读写能力。同一通道的结论前后相反，说明**能力必须实测、不能凭对话推断**。
2. **执行方自述被当作交付**：多轮出现「子代理说做完了」但落盘内容缺节、数字未同步的情况（另见 ADR-0013 的 D-042）。

## Decision

1. **角色铁三角**：用户 = 决策放行；Lead = 管理 + 审核 + 写规范/工单/文档/日志，**不写** `data/zh_cn/en_us/zh_tw/ja_jp/ko_kr` 数据文件；执行方 = 写数据文件（D-001）。
2. **自述不作证据**：执行方的「已完成」一律不可验收，交付以**落盘文件 + Lead 亲跑验收器**为准（D-017、D-021、D-055）。铁律「子代理自述不作证据」在通道迁移后仍适用。
3. **通道能力先实测再派单**：给执行方派活前，先用可复现的探测证明它真有能力（D-016 → D-021 的通道结论反转即教训）。子代理的模型选择同理：D-051 曾报 `child model selection is disabled`，D-052 实测在特定 provider/model 下已可用，并以子会话日志 `subagent/model-selection-policy` 为权威证据。
4. **分工可被用户按单覆盖**：D-050（角色直达面板整单派豆包）与 D-055（4.7 入库改派 DSH 子代理）都是**只覆盖该单**，不构成对 D-001 的一般性推翻；后续同类工单默认仍归 Lead。
5. **工单必须配 skill 与裁决**：子代理执行前明确「必载 skill / 按需 skill」，并钉死 skill 与本地规范的冲突裁决顺序（D-054）；不得把「已加载 skill」当作执行结果。

## Consequences

- **正面**：分工边界清晰，Lead 复核可复现；新通道接入有统一验证套路（探测 → 派单 → 复跑验收）。
- **负面**：Lead 需重复跑验收器，工作量固定在每单末尾；执行方不能自行宣布完成，节奏偏慢。
- **风险**：若把「用户按单覆盖」当成默认惯例，会侵蚀 D-001 的审核隔离；因此每次覆盖必须在该 issue / 工单中写明「仅此单」。
