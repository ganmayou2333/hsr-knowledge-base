## 一、这个库要成为什么

一个**可核对、可复现、可持续跟进版本**的《崩坏：星穹铁道》数据知识库 + 静态站：

| 目标 | 可验收的判据 |
|---|---|
| **数据可信** | 每个实体有官方来源；取不到写「待补充」并登记；`verify_fields` 异常 0 |
| **版本可跟进** | 新版本上线后 N 天内完成入库；版本基线写在 README 与 `metrics.md` |
| **多语言诚实** | 只收官方本地化原文；非官方内容逐文件标注工具/来源/时间；不冒充官方 |
| **站点可读** | 当前输入生成的页面死链 0；未收录内容明确降级；`verify_site[1]–[16]` 全绿；移动端不溢出 |
| **决策可追溯** | 每条口径有 D-* 或 ADR；`实测 > 决策 > 规范 > 叙述` 冲突时以此为准 |

## 二、五条主线（长期）

### 主线 A：版本跟进（每个版本一轮，硬节奏）

| 阶段 | 内容 | 验收 |
|---|---|---|
| A1 取证 | 官方内容 API（`iInfoId`）、米游社官方号、nanoka 静态 JSON | 官方清单条目落地为 issue |
| A2 入库 | 角色/光锥/遗器/活动/赛季/敌方/任务/场景 + 索引同步 | `verify_fields` 异常 0、索引计数自洽 |
| A3 镜像 | `zh_cn` + `en_us` 优先；ja/ko/tw 用官方本地化文本 | 结构对齐、缺项占位、不机翻 |
| A4 收口 | `build_wiki` + 四项验收 + `metrics.md` 刷新 + `update.md` 记 | `verify_site[1]–[16]` 全绿 |

**下两个节点**：4.8（预计 2026-12-23 前后）、5.0（大版本，需预留 schema 变更评估：新命途/新玩法/新类别）。

### 主线 B：多语言「官方原文替换」（official-text replacement，当前最大技术债）

现状：**23,049 个镜像文件**已打标为「非官方本地化」（`zh_tw`=zhconv、`en/ja/ko`=LLM，模型未记录）。长期路线是**把打标文件逐版本替换为官方本地化原文**：

| 阶段 | 动作 | 度量 |
|---|---|---|
| B1 | 优先替换**高频访问**（角色/光锥/遗器/活动）四语正文 | 打标文件数下降 |
| B2 | 官方 Wiki 对应语言词条 → 补物品/模拟宇宙 | 同上 |
| B3 | quest 剧情文本等不可得项：永久保留占位 + 登记（D-047 口径） | 不做即写清 |

> 只减不增：**新增内容一律官方原文**（D-065），打标数量是负向指标——已入真值表（`metrics.md` 的 `labeled_nonofficial_*` 四语 key，`verify_site[16]` 必填校验，D-078）。术语定义见 `GLOSSARY.md`「官方原文替换」。

### 主线 C：文档体系收敛

已完成：`GLOSSARY.md`、`docs/adr/`（主题聚合 + D→ADR 映射，规模与覆盖情况见 [ADR 索引](adr/README.md)）、`docs/metrics.md` + `verify_site[16]`、`update.md` 分卷（`docs/log/`）。**`docs/backlog/` 与 `docs/archive/` 按 D-075 缓建**（「内容没写好就先动结构」被否决），等内容线稳定后再评估。
后续工作以维护和复核既有文档为主：

| 动作 | 频率 |
|---|---|
| `python scripts/gen_metrics.py` 刷新真值表 | 每次入库/站点改动后 |
| 新增决策写 D-*，重大且难逆者升 ADR | 每次决策 |
| 术语新增进 `GLOSSARY.md` | 出现新概念时 |
| 是否归档一次性调研 | 按 D-075 在内容稳定后评估，不预设迁移目录 |

### 主线 D：站点与体验

现状：瑞士风锐角视觉 + 角色首次点击 hero 动画；六禁（无圆角/阴影/渐变/非图标图/外链）保持 0。
后续候选（按价值排序，需先立 issue）：

1. **站内搜索与可用性**：已支持标题、路径与正文开头摘要检索；继续验证摘要覆盖、键盘与移动端体验，见 [#34](https://github.com/ganmayou2333/hsr-knowledge-base/issues/34)。
2. **角色面板**：命途/属性/星级 之外的「版本维度」筛选
3. **详情页**：表格粘性表头与长页锚点导航（部分已有）
4. **性能**：`style.css` 已 44 KB（gzip 11 KB），若继续增长需拆分按页引用
5. **可及性**：全部页面 `prefers-reduced-motion` 与对比度 ≥4.5 的回归纳入验收

### 主线 E：事实正确性（正确性检查，2026-11-15 新增）

> 起因：PR #1 并入后长期没人核对「设定本身对不对」，直到 `2026-11-15` 才发现 `绒韬将军` 应为 `戎韬将军`、方壶/玉阙被镜像误标「已陨/失踪」、诛罗遗漏、P47 被当噪声删掉。**格式合规 ≠ 事实正确**，这条主线专门补这个洞。

| 阶段 | 动作 | 判据 |
|---|---|---|
| **E1 来源登记** | 每条设定性内容必须有来源（官方站/官方 Wiki/游戏内文本）；取不到写「待核实」并登记 `docs/待补充清单.md` | 抽查 20 条，缺来源 ≤2 条 |
| **E2 名号与编号对照** | 将军名号、称号、组织名、天才俱乐部编号、部门主管等**专名表**集中维护，与官方词条逐条比对 | 对照表 0 冲突；冲突即立 issue |
| **E3 状态字段枚举** | 状态类字段（仙舟现役/已陨、角色在位/离位等）只用白名单取值，不得即兴填 | `grep` 枚举外取值 = 0 |
| **E4 定期抽检** | **随版本收口跑（A4 加一步，D-078）**：本版改动条目 + 随机 10 条旧条目，与权威源比对 | 差异清单写进当版收口 issue；确证错误当版修复，无源条目登记台账 |
| **E1 粒度（D-078）** | 设定性内容（世界观/剧情/社区投稿段落）**段级**标来源；数据文件已有头部元信息不重复加 | 新增设定段落 100% 带出处 |
| **E1 存量回溯（D-078）** | 只回溯**高危区**（社区投稿并入的段落，如 PR#1 类）；其余存量靠 E4 滚动覆盖 | 高危区 100% 有来源行或「待核」标注 |
| **E5 已知错误模式库** | 记录已发生的错误类型，作为下次检查清单：①错字/音译（绒韬→戎韬）②状态误标（方壶、玉阙）③遗漏（诛罗）④**整改时误删真实信息**（P45/P47/P48 被当噪声清理）⑤权威源更新滞后（HoYoWiki 只列 6 位大君） | 模式库 ≥5 条并持续追加 |

> 全部细则的裁定记录 = **D-078** + `ADR-0018`；专名对照见 `docs/专名对照表.md`。

**自动化能做的（进 `verify_*`）**：

- 专名表一致性：`GLOSSARY.md` 与数据正文的专名写法比对（如「戎韬」出现即校验拼写）；
- 状态枚举白名单校验（仙舟：`现役|已陨`）；
- 「待核实」标注覆盖率：凡含未确证断言的段落，必须出现「待核实」或来源 URL。

**自动化做不了的（必须人工）**：数值与效果是否与官方一致、剧情归属与时间线、人物关系断言——靠 E4 抽检 + Reviewer 只读复核。

## 四、质量闸门（每次合并前必须）

```bash
python wiki/build_wiki.py            # 页数随输入变化；死链 0，未收录内容按预期降级
python tools/verify_site.py          # RESULT: PASS（[1]–[16]，[5] 六项 0）
cd data/zh_cn && python ../../scripts/verify_fields.py   # 异常 0；待补充数随数据变化（必须在 data/zh_cn 目录）
cd .. && python scripts/verify_links.py          # exit 0，数据区死链 0
```

附加要求：

- **正确性闸门（主线 E）**：改动涉及名号/称号/编号/状态字段时，必须附「对照表 + 来源 URL」；
  社区投稿并入的段落一律视为「未核」，合并后必须做一次 E2 对照；
- **不得以格式合规代替事实核查**：`verify_site`/`verify_fields` 全绿 ≠ 内容正确（`2026-11-15` 实例：`绒韬` 错字与三艘仙舟状态误标在四项验收全绿的状态下存在）；
- 数据目录零改动时，`verify_fields` 数字不得变化；
- 站点改动需真实浏览器验收（1280×800 / 600×900、键盘、`prefers-reduced-motion`）；
- 提交信息引用 issue（`closes #N` / `refs #N`），推送后用 `gh api` 或 `ls-remote` 复核。

## 五、风险与不做清单

| 风险 | 缓解 |
|---|---|
| 版本更新节奏压过产能 | 主线 A 只做「官方已公布」的内容，剩余进 `docs/待补充清单.md`，不编造 |
| 镜像长期非官方化 | 打标是诚实的下限；B 线逐版本替换，指标只看「打标数下降」 |
| 生成器/验收器硬编码 | 类别从文件系统推导（D-041）；新增类别必须同时改 `SIDENAV` 与 `verify_fields.classify` |
| 站点样式与验收器冲突 | 六禁以 `verify_site[5]` 为唯一判据；不得用 SVG 渐变/投影绕过 |
| 外部贡献降低规范 | 外部 PR 先 review 再合并；不 squash 以保留作者提交；合并后我方按规范修正 |
| **格式合规掩盖事实错误** | 主线 E：专名对照表 + 状态枚举 + 每版抽检；社区投稿视为「未核」直至 E2 对照完成 |

**明确不做**：解密客户端 `ENCR` 包取游戏内文本（绕过内容保护）、用机翻补正文、为「看起来完整」建占位条目、把非官方内容标成官方。

## 六、本文档怎么维护

1. **不进日期流**：里程碑状态改动直接改本文件（`update.md` 仍按版本卷记录日常）。
2. **每次完成里程碑**：更新对应行 + 在 `docs/metrics.md` 留当时的真值快照。
3. **口径变化**：先改 `docs/adr/` 或 D-*，再改本文件——不得本文件与决策记录打架。
4. **季度复核**：删掉已无意义的条目，而不是让它长期躺在「计划」里。
