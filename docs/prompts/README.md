## 一、为什么要拆

单文件版已 452 行，且每个游戏版本都会更长（4.6 → 4.7 → …）。拆成 **「常驻核心 + 版本参数 + 按需模块」** 后：

- 新版本只改 **1 个参数文件**（核心与模块不动）
- 按任务只装载需要的模块，装载量可预测
- 256k 缓存里始终留足产出余量

## 三、256k 预算模型

| 区块 | 预算 | 占比 | 说明 |
|---|---|---|---|
| 常驻：核心 + 参数 | ~9k | 3.5% | 每次会话都装 |
| 常驻：规范文件 | ~20k | 8% | 格式规范 + 数据来源；其余按任务 |
| 按任务：模块 | ~3k | 1% | 剧情 / 翻译 / 对账 |
| 按类：基准文件 | ~8k | 3% | 每类 1 个 |
| **装载小计** | **~40k** | **约 16%** | 最省场景；全装也不过 ~80k |
| 对话历史 + 产出 | ~150k | 59% | 主战场（如批量写剧情文件） |
| 安全余量 | ~66k | 26% | 防溢出 |

**结论**：256k 足够「全量装载 + 长产出」。真正的风险不是装不下，而是**装载了无关内容**（如整份 33k 的待办清单）导致注意力稀释。

## 五、组装方法（三步）

1. **贴常驻**：`10_核心_版本无关.md` → `20_参数_4.6.md`
2. **贴模块**：按第四节矩阵，贴 `30_模块_剧情获取.md` 等
3. **传附件**：把该任务需要的规范文件作为附件上传（读不到就走核心里的【附录 F】兜底，并声明）

> 单文件组装版已包含以上全部内容，二选一即可：
> - **图省事** → 直接用 [`豆包提示词_4.6版本建库.md`](../豆包提示词_4.6版本建库.md)
> - **要长期维护 / 控预算** → 用本目录模块化装载

## 六、版本迭代规则（4.6 → 4.7 只动一个文件）

1. 复制 `20_参数_4.6.md` → `20_参数_4.7.md`，只改参数块（版本号、收录日期、规模、已入库统计、本轮缺口）
2. `10_核心_版本无关.md` **不动**（不含任何版本硬编码）
3. 模块按需增补（如新增玩法 → 新增 `4x_模块_<玩法>.md`）
4. 在 `update.md` 记一条日志

## 九、角色分工与工单 / 审核流程

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **你（用户）** | 决策、放行、最终验收 | — |
| **豆包（工作模式）** | **执行**：调研、建库、写文件、跑脚本、出报告 | 不自行改口径、不越权删改存量、不把摘要当原文 |
| **主管（Lead · 我）** | **接收**豆包输出 → **审核** → **出下一轮提示词**；管理 `docs/prompts/` 与 **256k 装载预算** | **不下场写 `zh_cn/` 数据文件**、不代豆包执行、不改豆包产出（只出问题清单） |

### 主管固定职责（六条）

1. **接收**：收下豆包每轮交回的产出与证据（文件路径 / 行号 / 命令输出 / 来源 URL）。
2. **审核**：数字 grep/glob 实测复核、随机抽 hash 回 TextMap 逐字比对、越权与格式检查 → 出「**通过** / **打回（附具体问题与证据）**」。
3. **出提示词**：按下一轮任务组装装载包（核心 + 版本参数 + 按需模块 + 附件清单 + 工单），并**控制在 256k 内**。
4. **维护**：`docs/prompts/` 的模块、预算表、装载矩阵、工单模板、版本参数；新版本只改参数文件。
5. **升级**：口径冲突、越权请求、需求歧义、数据源缺失 → 交你裁定，不自行拍板。
6. **不越界**：不写 `zh_cn/` 数据文件、不代豆包跑脚本、不直接改豆包产出。

### 256k 装载纪律（由主管把关）

| 区块 | 预算 |
|---|---|
| 常驻：`10_核心_版本无关` + `20_参数_<版本>` | ~9k |
| 规范文件（按任务取）：格式规范 12k / 行动准则 7k / 三月七示例 8k / 翻译办法 6k / 数据来源 2k | 取 2–3 份 ≈ 20k |
| 按任务模块：`30_模块_剧情获取` 等 | ~3k |
| 基准文件：每类 1 个 | 3–8k |
| **单轮装载上限** | **≤ 80k（31%）**，留给对话与产出 ≥ 176k |
| 禁止 | 整份装载 `待办清单.md`（33k） |

**工单流程**

1. Lead 写工单（模板见 `工单_4.6对账.md`）：任务 / 交付物 / 证据要求 / 已有基线 / 验收标准
2. 你放行 → 豆包执行
3. 豆包交回产出 + 证据（文件路径、行号、命令输出、来源 URL）
4. Lead 审核：逐条对照验收标准 → 出「通过 / 打回（附具体问题与证据）」
5. 通过后由豆包写 `update.md` 日志，Lead 复核日志格式与时间戳

**Lead 审核取证手法（必用）**

- 数字一律 grep / glob **实测**，不采信报告里的数字
- 抽 hash 回 TextMap 原文**逐字**比对（防「摘要冒充原文」）
- 检查引用是否逐字（间隔号 `•`、书名号《》、全角括号）
- 检查日志时间戳是否超前、术语是否与官方一致
- 检查是否越权改动了存量文件

## 附录 · 精确测量命令

在本机（Shell 正常）执行，替换 `G:\HSR` 下的目标文件：

```python
# measure.py —— 中文按 0.6 token/字符粗估，英文/数字按 0.25
import pathlib
files = [
    "格式规范与要求.md",
    "翻译办法.md",
    "数据来源.md",
    "docs/多语言数据查找行动准则_DeepSeek.md",
    "docs/三月七_冰_四星_详细示例.md",
    "docs/prompts/10_核心_版本无关.md",
    "docs/prompts/20_参数_4.6.md",
]
for f in files:
    t = pathlib.Path(f).read_text(encoding="utf-8")
    print(f"{f}\t{len(t)} 字符\t约 {int(len(t) * 0.6)} token")
```

> 若豆包支持显示 token 数，以它的计数为准；本表估算仅用于装载决策，误差 ±30% 不影响结论。
