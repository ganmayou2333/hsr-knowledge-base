## 三、目录结构规范

### 3.1 多语言目录结构
```
G:\HSR\

│   ├── character/
│   ├── lightcone/
│   ├── relic/
│   ├── items/
│   ├── simulated/
│   ├── quest/
│   └── worldview/
├── zh_tw/                    # 繁体中文
│   └── ...
├── en_us/                    # 英语
│   └── ...
├── ja_jp/                    # 日文
│   └── ...
└── ko_kr/                    # 韩文
    └── ...
```

### 3.2 文件命名规范
- 文件名与简体中文版保持一致（使用ID或官方名称拼音/英文）
- 示例：
  - `zh_cn/character/毁灭/克拉拉_物理_五星.md`
  - `en_us/character/毁灭/Clara_Physical_5Star.md`
  - `ja_jp/character/滅/クララ_物理_五星.md`

### 3.3 文件内容结构
每个多语言文件应包含：
```markdown
# [角色名/物品名]（目标语言）

## 基本信息
- 简体中文名：XXX
- 英文名：XXX
- 日文名：XXX
- 韩文名：XXX
- ID：XXX

## [分类字段，如技能/描述/故事等]
（目标语言内容）

## 翻译说明
- 数据源：XXX
- 翻译时间：XXX
- 校对状态：未校对/已校对
```

## 四、执行步骤

### 阶段一：数据探查与规划（预计10万token）
1. 扫描StarRailRes多语言JSON文件，统计各语言覆盖度
2. 对比现有简体中文数据库，列出需要多语言化的文件清单
3. 建立ID对照表（简体中文ID ↔ 多语言ID）
4. 输出：`docs/multilang_coverage_report.md`

### 阶段二：基础数据迁移（预计50万token）
1. 从StarRailRes提取角色、光锥、遗器的多语言基础数据
2. 按目录结构创建多语言文件夹
3. 生成基础多语言文件（名称、描述、技能等结构化字段）
4. 优先完成P0目录：character/lightcone/relic
5. 输出：各语言目录下的基础文件

### 阶段三：物品与模拟宇宙数据（预计80万token）
1. 从StarRailRes提取items多语言数据
2. 提取simulated祝福/奇物/事件多语言数据
3. 处理大量条目时的批量生成与校验
4. 输出：items/和simulated/多语言文件

### 阶段四：剧情与任务数据（预计100万token）
1. 从Fandom Wiki等提取英文剧情文本
2. 从官方渠道提取日/韩文剧情数据
3. 对齐简体中文剧情结构，生成多语言版本
4. 输出：quest/多语言文件

### 阶段五：校验与补全（预计50万token）
1. 交叉验证多语言数据的准确性
2. 补全缺失字段（使用翻译工具辅助）
3. 建立多语言索引文件
4. 输出：`docs/multilang_index.md`、校验报告

## 五、Token暂停规则（核心约束）

### 5.1 暂停阈值
**每处理满100万token，必须暂停执行，并向用户报告进度。**

### 5.2 暂停时必须输出
1. **已完成工作量**
   - 已处理文件数 / 总文件数
   - 已消耗token数（估算）
   - 当前所在阶段

2. **已生成产物清单**
   - 新增文件列表（按目录统计）
   - 已更新文件列表
   - 中间产物（报告、对照表等）

3. **遇到的问题与决策点**
   - 数据源缺失
   - 翻译歧义
   - 结构不一致
   - 需要用户确认的事项

4. **下一阶段计划**
   - 下一步具体操作
   - 预计token消耗
   - 预计完成时间

### 5.3 暂停后的恢复
- 用户确认继续后，从暂停点恢复执行
- 不得跳过暂停检查点
- 如用户提出修改意见，优先处理修改意见再继续

### 5.4 Token估算方法
- 中文：1字符 ≈ 1.5 token
- 英文：1单词 ≈ 1.3 token
- 日文：1字符 ≈ 1.5 token
- 韩文：1字符 ≈ 1.5 token
- 代码/JSON：按字符数 × 0.5 估算

## 六、质量要求

### 6.1 数据准确性
- 优先使用官方数据源，翻译工具仅作辅助
- 关键名词（角色名、技能名、物品名）必须与官方一致
- 翻译需符合游戏语境，避免机翻感

### 6.2 结构一致性
- 多语言文件结构与简体中文版保持一致
- 字段顺序、标题层级、表格格式统一
- ID系统完全对齐

### 6.3 完整性
- 每个文件必须包含所有对应字段
- 缺失字段需标注「待补充」并记录原因
- 定期运行完整性校验脚本

### 6.4 可追溯性
- 每个文件标注数据源和翻译时间
- 重大翻译决策记录在`docs/translation_decisions.md`
- 保留原始数据快照，便于回滚

## 七、工具与脚本

### 7.1 必备脚本
- `scripts/extract_multilang_from_srr.py`：从StarRailRes提取多语言数据
- `scripts/verify_multilang_coverage.py`：校验多语言覆盖度
- `scripts/generate_multilang_index.py`：生成多语言索引

### 7.2 校验命令
```bash
# 校验文件数对齐
python scripts/verify_multilang_coverage.py --check count

# 校验字段完整性
python scripts/verify_multilang_coverage.py --check fields

# 生成覆盖率报告
python scripts/verify_multilang_coverage.py --report
```

## 八、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 官方数据源缺失某语言 | 数据不完整 | 标注缺失，使用翻译工具辅助，记录待官方补充 |
| 翻译质量不达标 | 用户体验差 | 建立校对流程，关键内容人工复核 |
| 目录结构迁移出错 | 数据混乱 | 先备份再迁移，分批执行，每批校验 |
| Token超限未暂停 | 违反约束 | 每阶段开始前估算token，设置检查点 |
| ID对照表错误 | 数据错位 | 建立自动化校验，交叉验证多语言ID |
